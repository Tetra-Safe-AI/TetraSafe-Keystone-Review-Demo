# How the version 20 demonstration is put together, and what that means for its evidence (review version 4)

**For:** private review. **Drawn from:** the delivered version 20 source (archive `3bb5fb7f…`), read-only. **Goes with:** `keystone_v20_architecture_for_review_v4.svg`.

This describes the demonstration **as tested**. It is not a design for prevention, and it names components without disclosing their implementation.

## The components

**Inside the Keystone virtual machine, the restoration domain.** Everything here is rolled back when the VM's disk is restored:
- **The agent**, which is untrusted. Its own key was created before the snapshot, so the restored disk still has it.
- **Admission and the issuer**, which approve a refund and issue an authorization intended for single use.
- **The intermediary: the execution boundary.** It checks the authorization's signature, that the presenter holds it, and that it matches the request. It asks the **anchor** whether the authorization was already used, claims it in its own **store**, and then sends to the provider. **This is the only place the decision to send is made.** The anchor and the store are SQLite files inside the VM.
- **A simulated provider**, whose execution ledger is also inside the VM.
- **The recorder:** every component writes its events to recorder logs.
- **The signed shipper.** It reads the recorder logs **read-only**, and signs each copy with the VM's key, K_ship, together with a counter kept on the VM's disk. It opens no other Keystone file and connects to no Keystone socket.
- **A tunnel account** that can do nothing but forward to the witness.

**On the host computer, outside the restoration domain:**
- **The witness.** It receives the shipper's messages on a TLS endpoint with a pinned certificate, and keeps them in its own log. It signs its replies and its periodic checkpoints with its key, K_store, and serves the dashboard.
- **The co-signer**, which co-signs each checkpoint with Stephen's co-signing key, K_witness, generated by setup.
- **The demo program**, which operates everything: it starts the witness, the co-signer and the tunnel; runs each step inside the VM over SSH; reads results back over SSH; asks VirtualBox to power off, snapshot and restore; and builds the evidence bundle.
- **The agent's kept authorization.** After Step 2, the VM returns a copy of DEMO-1's signed authorization and its obligation, with no private key, to the demo program over SSH. The demo program keeps it outside the VM through the restore, standing in for an agent that is not inside the boundary's machine.
- **The verifier and the saved-evidence viewer**, used only after the run.

## How Step 8's authorization survives while the boundary's memory of it does not

1. **Step 0, before the snapshot:** the VM creates Keystone's world, including agent_a's key.
2. **Step 1:** the snapshot is taken with the VM powered off. The agent's key is part of it.
3. **Step 2, after the snapshot:** DEMO-1's authorization is issued and used. The anchor and the intermediary's store record its use. A copy of the authorization goes to the demo program on the host.
4. **Step 4, the restore:** the VM's disk returns to the snapshot. The anchor and the store no longer have any record of DEMO-1. The agent's key is still there, because it predates the snapshot. The kept copy is still on the host, because it was never inside the VM.
5. **Step 8:** the demo program sends the kept copy back into the VM over SSH. agent_a presents it, proving possession with its surviving key. The anchor answers "not used", the intermediary sends, and the witness, which kept the Step 2 send, now sees two sends under one authorization.

## Answers to Kiro's questions

**1. How does the witness learn what the VM did, and what prevents spoofing?** The shipper sends signed copies of the recorder's events over a reverse SSH tunnel, opened from the host, to the witness's TLS port. A message is accepted if it is signed with K_ship. **Nothing prevents the VM itself from sending false messages:** whatever holds K_ship can sign anything. What the witness can observe is the shipper's **counter going backwards**. That is consistent with a restore, because an honest machine's counter is rolled back with its disk. The witness cannot establish what caused it: a machine holding K_ship could send a lower counter deliberately, or send false events with a counter that never goes backwards. In this run, counter 3 arrived after 26 had been accepted, which is consistent with the Step 4 restore that the demo program performed. The witness cannot detect a **dishonest** machine.

**2. Is Step 8 a bug or a fundamental limit?** It is a limit **of this implementation**. Its outcome was stated in advance: record 250, written when Step 8 was added and before any run on real VirtualBox, gave the expected result as "regains authority and is sent again". That prediction came from an earlier experiment, record 220 (pre-registered in record 219). That experiment was a **simulated** memory restore on **different code**, not frozen run 7. The first stand-in runs of Step 8 are reported in the same record 250. The intermediary's memory that an authorization was used, held in the anchor and its store, lives inside the restoration domain. After the restore it answers "not used", and nothing outside the VM is consulted. The anchor is independent of the other Keystone components, but not of the restoration.

**3. Why does the witness observe rather than prevent?** In version 20 the witness is deliberately observational. The frozen run 7 boundary was tested unmodified. The witness's signed reply goes only to the shipper, which uses a rollback flag to re-send its logs; it never reaches the intermediary. Preventing the second send would need the boundary to consult a record that survives the restore, **before** sending. That changes the boundary itself, including what it does when that record is unavailable. It is a different and stronger claim, and it is not demonstrated here.

**4. What would a third-party witness deployment change?** The witness and its keys would run on equipment the operator doesn't control, with keys generated and kept by that third party. That would address independent custody. It would not, by itself, make the VM's messages true (see 1).

**5. Why are 11 observations unauthenticated?** The demo program gets them by asking the VM directly over SSH, not through the signed shipper. Signing them would make their **records** authenticated. It would not make their **contents** independently trustworthy, because they would still be reported by the machine under test.

## What PASS means here

The verifier's PASS means:
- the evidence's hash chain is intact;
- every message and checkpoint is signed by the keys involved;
- the checkpoints are co-signed by the co-signing key the operator supplied;
- the captured views follow from the signed log.

In short, the records are internally consistent with those keys. **It cannot show that what was signed was true, or that someone holding the keys did not construct and sign a different record,** and it is not an independent audit. Every key, every program and the VM ran on one computer operated by one person.

## What would strengthen the trust root (future work, not part of this run)

- Give the co-signing key's fingerprint and the package's manifest value to a reviewer **before** a run.
- Have someone else operate the experiment on their own equipment, generating and keeping the co-signing key themselves.
- Have someone else write a checker from a description of the bundle format.
- Run the witness on a separate machine.
